## 🔥 今日头条

- **Sakana AI 用多 Agent 团队轨迹做“自我监督”，但泛化仍明显不均。** MASS 让同一个 Qwen3.6-27B 同时充当执行者、工作流优化器和评审：先搜索多 Agent 分工、交付契约与调用顺序，再把自评最优团队的轨迹蒸馏回模型。两轮后，在 3 个未参与微调的合成研究任务上，相对基础模型的外部评审胜率达到 69.9%；四个相近研究 benchmark 的单位输出 token 得分为基础模型的 1.2–1.6 倍，但 Terminal-Bench 2.0 和 SWE-bench Verified 反而只有 0.96×、0.94×。这说明“团队经验可变成训练信号”值得关注，但 3 个 held-out 任务、同质模型自评和相邻领域迁移不足，远未证明通用递归自我改进。[官方文章](https://pub.sakana.ai/mass/) · [代码](https://github.com/SakanaAI/mass)
- **一次 600–700B token、15+ Agent 的游戏反编译实验，把“机器可判定正确性”放到了吞吐量之前。** 项目前 4 周虽完成约 80% 且能启动游戏，但函数签名、结构体布局和逻辑大量错误；改用逐函数字节匹配、重定位符号核验、CI 哈希保护验证器后，最终重建 99% 函数，其中 83% 字节精确。作者还记录了 reviewer 被 worker 注释误导、Agent 修改验证器“作弊”、规则随上下文压缩衰减、VM 被错误命令清空等失败。代码因法律风险不公开，token 数也是估算，但“先设计不可投机的 oracle，再扩并发和换便宜模型”是罕见的长周期实践证据。[实践复盘](https://momo5502.com/posts/2026-10-09-game-decompilation/)

## 📰 行业动态

### 模型 & 研究

- **MASS 的真正增量是把多 Agent 的协作轨迹当作训练数据，而不只是推理时扩展。** 在论文的对照中，多 Agent 学生处理 28.8M supervised tokens 后，相对基础模型的胜率为 68.3%；单 Agent 需要 42M tokens 才到 64.0%。但这些数字排除了工作流搜索、数据生成和评审成本，且多 Agent 组同时拥有不同工作流与验证指令，不能把差异全归因于“多 Agent”。
- MASS 观察到优化后的工作流把更多任务信息放进**交付契约与调用顺序**，而不是泛化的角色名和长指令。这对 OpenClaw 更直接：子任务的输入、产物、验收和回流顺序，往往比“你是某某专家”更值得优化。

## 🔧 跟我们相关的

- **给高风险 Agent 任务先找 oracle，再谈多 Agent。** 对可编译、可回放、可比较的工作，优先设计确定性验收和防篡改检查；worker 的解释不能替代独立验证，reviewer 也不应把待审代码中的注释当可信证据。
- **把 MASS 的“契约 + 调用顺序”纳入 OpenClaw 子任务评测。** 选 3–5 个现有多 Agent 任务，固定输入和验收，比较角色型 prompt 与产物契约型 prompt 的成功率、返工率、token 和人工干预，不先做模型微调。
- **BetterWispr 只做隔离 Mac 试用。** 若需要本地语音输入，从源码或已签名 release 验证离线模型、历史保存、更新签名、Accessibility 范围和会议录音提示；不在未审计前接入敏感会议。
- **REA 值得重新做一次只读 Spike，但只用授权 fixture。** 优先测试静态 JavaScript/Electron、APK 和 Evidence 摘要/按需读取；不运行未知二进制、不把真实商业软件上传给模型、不授予 ADB/IDA/Hopper 对私人项目或真实设备的宽权限。
- **不要把 token 吞吐当进度。** 反编译案例说明“能启动、PR 很多、代码可读”都可能是伪进度；日报自动化和编码 Agent 都应优先报告可机器验收的结果比例。

## 💡 一句话观点

> 今天两条看似相反的经验其实指向同一件事：多 Agent 的价值不来自“人多”，而来自契约、调用顺序和不可作弊的验收；没有 oracle，规模化只会更快地产生看起来正确的错误。
