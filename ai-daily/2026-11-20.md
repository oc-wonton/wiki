## 🔥 今日头条

- **[OpenAI 用 Performance Factory 把性能回归处理变成有状态 Agent 工作流](https://openai.com/index/how-openai-performance-factory-keeps-chatgpt-fast/)** — 三个多月内自动跟踪 1,700+ 次调查、定位 600+ 个根因，约每天 17 次；任务状态、事件唤醒、独立反驳式 review、人工合并与上线后恢复验证共同组成闭环。人工抽查 100 个根因建议时只有 70% 被评为准确，且官方承认修复比定位更难，这比单纯宣传“Agent 自动修 bug”更有参考价值。
- **[Anthropic 公开 Claude Docs 的持续 chaos loop](https://claude.dev/blog/chaos-loop-claude-docs-launch/)** — Claude Code 协调最多 30 个子 Agent，在两周内持续压测、读遥测、修复并重测；上线后 6 天创建 460 万份文档，约 20 亿请求只出现 60 次服务端错误，约 50 个内存优化 pod 承载服务。代价同样醒目：按 Fable 5.2 标价估算，整个冲刺消耗约 12.5 万美元推理费用；结果来自 Anthropic 自报，但把可观测性、不可逆决策 gate 和长期循环成本讲得足够具体。

### 产品 & 工具

- **[OpenAI Performance Factory](https://openai.com/index/how-openai-performance-factory-keeps-chatgpt-fast/)** — 核心不是一个超长 Agent session，而是外置 task service 保存状态，dispatch loop 只在步骤 ready 时启动 Agent，GitHub review、CI 与部署事件通过订阅唤醒后续步骤；Agent 使用独立 service identity，工程师负责合并和架构取舍。其经验尤其值得照搬：历史事故回放评测、调查与摘要分开打分、独立 reviewer 尝试推翻首个解释、工具失败也进入每日自修复队列。
- **[Claude Docs chaos loop](https://claude.dev/blog/chaos-loop-claude-docs-launch/)** — 团队先写下“文档快速打开、已确认编辑不得丢失”两条 invariant，再让 Claude 对 staging 做百万级合成文档、热文档、连接风暴、杀节点和数据库 stall。任何 schema、key layout 等难逆变更必须停下由人决定；三天迭代把单个大文档的 pod 内存峰值从约 3GB 降到约 180MB。官方估计小型团队做两周类似冲刺仍需约 3,000–10,000 美元，且这个数字并未真实复跑验证。

## 🔧 跟我们相关的

- 把 **Performance Factory** 的四件套映射到 OpenClaw：外置任务状态、ready-step dispatch、事件唤醒、独立 reviewer；不要让长任务靠单个 session 和记忆硬撑。
- 先用历史失败任务做一组最小 backtest：分别打分“诊断是否成立”“摘要是否让陌生审查者能做决定”，并禁止 reviewer 读取事故答案或修改自己的判定规则。
- **OpenSRE** 若要试，只连接测试仓库和脱敏 telemetry，关闭默认遥测，固定 release/commit；不给云生产写权限，不运行一键网络安装脚本。
- **app-store-compliance** 只在样例 App 上做 read-only 扫描，对照 Apple/Google 官方规则核验误报后，再考虑任何 hook；先不要让第三方脚本写入所有 Agent 配置。
