# 阅读：QQ 飞车 Agentic 研发转型中的 Loop Engineering

原文：<https://mp.weixin.qq.com/s/FTUowOWA8kbzGJ21DA4PoQ>

作者任磊达，腾讯高级后台开发工程师、QQ 飞车项目组 Agent 落地负责人。文章来自 AICon 2026 深圳演讲整理，背景是每月约 300 亿 token 的高强度实践。

## 核心定义

Loop Engineering 不是让定时任务重复执行，也不是持续改 Prompt，而是把一次人工纠错沉淀为可观测、可验证、有边界的工程反馈回路，使同类错误不再重复：

```text
触发 → Agent 执行 → 确定性检查/人工反馈 → 自动修复 → 再验证 → 经验回灌
```

Harness 提供模型、工具和运行环境；Loop 锚定具体业务目标，把模型的概率性输出通过迭代变成可交付结果。重点不是 token 成本，而是减少人的认知和注意力负担，并明确 human-in/on/out-of-the-loop 的位置。

## 四层实践

### 1. Hook 级闭环

文件写完立即运行自定义 Linter，用增量 diff 报错，把错误回流给 Agent 自动修复；pre-commit 再跑更完整、耗时更长的检查。核心判断是：Rules 只是要求概率模型“不犯错”，属于许愿；硬约束应由 Linter 执行。

需要处理 CLI 兼容、Linter 并发、超时放行，以及 Agent 跳过检查的问题。

### 2. CI / MR 级闭环

特性分支推送后自动创建 MR；Linter、Review 等流水线并行执行；失败阶段把诊断交给 Agent 修复并重新推送，触发下一轮验证。对明确“永远不会人工 Review”的低风险改动，才允许规则化 auto-approve/merge。

MR 评论成为可持久化反馈入口：机器先按规则提问，Agent 回答和修复，人对错误答案继续评论，经验再回灌。Issue 流转、冲突修复等脏活也可用定时 Loop 处理。目标是让机器负责发现，人只处理例外。

### 3. Workflow 级闭环

工作拆为事前、事中、事后：

- 事前：人做决策，用苏格拉底式提问把模糊需求变成结构化文档。
- 事中：Agent 自主实现；测试策略由独立 Agent 先设计，避免自写自测。人与 Agent 不在中途随意聊天，避免反馈散落在日志。
- 事后：人通过 PR/MR Review 给出评论，形成持久、可回放的反馈数据。

Review 不应只是并发召唤多个模型制造噪声，而应按安全、架构、性能等不同视角分给专门 reviewer，再结构化合并。大改动若文档不足，应由 CI 触发文档补全，降低人的理解成本。

### 4. 团队 Graph Engineering

个人工作台和私有 Loop 只是局部脚本。要转化为组织能力，需要把任务依赖、共享能力和反馈关系编排成 Graph，并把通用能力插件化。复用不应等于把同一套庞大 UI/流程强塞给所有人，而可以让 Agent 参考其他人的组件后在当前场景重新组合。

作者主张“场景化 SDD”：每个需求可以有自己的上下文和流程，让每个人参与改进；共性再回灌到底层组件，而不是少数人制定一套全员被动使用的巨型 SDD。

## 度量

Loop 是否进步可看：

1. MR 人工评论数量下降；
2. 重复评论占比下降，即同类问题“不二过”；
3. 事前澄清耗时下降；
4. 人工介入点和例外数量减少；
5. 自动修复后的再验证成功率提升。

这些指标必须同步改善，否则只是烧更多 token。

## 关键踩坑

- 上下文膨胀：个人 SDD 不断积累可超过 600k；应采用入口 Skill → 二级路由 → 按需三级内容，把活跃上下文压到约 100k。
- Subagent 递归：Skill 内无边界 fork 可能递归烧掉数亿 token，必须设置深度、轮次、预算和停止条件。
- 防御性扩张：简单数据转换任务因模糊 goal、过高思考、MR 级 reviewer 和自动修复互相放大，一天生成 4 万行、200 条评论、27 轮评审，最终关闭 MR。
- 测试债务：只追求覆盖率会制造锁死代码的低价值测试。应风险驱动，并让测试设计与实现 Agent 分离。
- 无界 Loop：每个循环都必须有 max turns、预算、变更规模、升级人工和终止条件。

## 判断

文章最有价值的不是“四层”命名，而是三个工程原则：

1. **概率生成，确定性验收**：把硬规则下沉到 Linter、测试、CI 和权限系统。
2. **反馈必须落在可持久化边界**：PR 评论、失败诊断、结构化文档比聊天日志更适合回灌。
3. **Loop 必须有界**：自动修复不是无限重试；规模、轮次、token、权限和人工升级都要设上限。

需要保留的质疑：分享给出了大量实践和失败案例，但缺少成功率、返工率、缺陷逃逸率、成本和基线对照等量化数据；“同工作区并发修改高饱和文件，让模型即时修冲突”风险较高，不应直接替代独立 worktree，应先有实验数据。

## 对当前体系的启示

- OpenClaw 管触发、状态、失败告警和人工交互；OMP 管实现；CI/Linter 管硬验收。
- AI-Native SDLC 的 intent/spec/plan 是事前结构，OMP 实现是事中，PR Review 是事后。
- 建立 bounded loop contract：max turns、token/时间预算、最大 diff、最大修复轮数、允许工具、停止和人工升级条件。
- AI 日报去重账本是一个小型 Loop，但还需要 Golden Set 和投递验收，避免“任务成功、用户没收到”。
- Skill 内容采用 Router + 按需加载，禁止把所有经验注入常驻上下文。
- 每次人工重复评论应先变成确定性检查；无法确定化时才进入 Skill/Memory。
